# 21 Prevention-first guidance for Warrant

## Goal

讓 Warrant 的起草與實作指引體現「優先以程式結構預防錯誤，其次用有效的自動檢查，再保留需要判斷的文字與人工審查」的順序，同時維持人類選擇工作、核准意圖、範圍不可自行擴張及證據決定完成的界線。這次改善的對象是 `plugin/skills/warrant/` 的技能與採用區塊，不是替本 repository 另找程式改造案例。以既有 eval 機制觀察修改前後的實際 agent 行為；交付規則與觀察結果，不宣稱已證明普遍品質提升或審查成本下降。

## Out of Scope

- 改變三條核心規則、核准方式、Story 的三個二級章節、宣告驗證指令的權威、完成回報格式或後續驗證分類。
- 自動選工作、讀取私人聊天或公司 repository、挖掘歷史回饋的新工具，或把架構改善當成擴大既有 Story 的授權。
- 向採用端發佈腳本、CLI、套件、通用檢查框架；不新增工作模式、必填狀態欄位、第四個 Story 章節或額外完成回報章節。
- 強制所有工作先重構、為純文件或判斷問題製造測試、承諾杜絕所有錯誤，或把人工核准與必要的風險判斷視為應移除的負擔。
- 修改網站功能、CI/release workflow、既有 eval 的通過標準，以及其他 Story。保留 Story 20 的 README 檢查變更與既有 `site/package-lock.json` 變更，不混入本次成果。
- 自動 commit、push、發佈或部署；統計顯著性、跨模型普遍效果與人工工時改善研究。

## Acceptance Criteria

1. `plugin/skills/warrant/SKILL.md` 在既有起草及實作步驟內加入精簡指引，不新增模式：先檢查已核准範圍內是否能在擁有該行為的型別、介面或模組消除錯誤途徑；其次以採用端既有工具建立可重現的自動檢查；文字保留給仍需判斷的限制與理由。指引明確說明這是依問題選擇手段的順序，不是每項工作必做的三道流程，也不是擴大重構的授權。以逐條文字審查對照此項與第 2、3 項。
2. 對可重現缺陷，起草時要求把已知錯誤行為與允許行為寫成可觀察的驗收條件；在獲准的實作範圍內，要求實際觀察保留的檢查會拒絕錯誤、接受正確行為，並由專案宣告的驗證路徑執行。錯誤案例使用隔離副本或 fixture，不污染使用者工作樹。既有檢查足夠時重用，不要求重建。不能取得觀察時如實回報；不得以測試檔存在、文字匹配或推論充當有效性的證明。這些指引不得追溯改寫已核准 Story，也不得自行替換宣告驗證指令；需要新增或更動驗收標準時交人核准。
3. 對當次授權來源中已出現的重複回饋，指引要求優先辨識可移交結構或自動檢查的具體問題；若解法超出目前 Story，只提出問題、證據與可驗收的後續工作建議，交人決定是否另寫／核准 Story，不自動建立工作佇列、改寫現有 Story 或開始改造。僅有判斷需求時保留簡短理由與必要人工審查，不為滿足順序新增無效檢查。
4. `plugin/skills/warrant/agents-block.md` 包含同樣的核心優先順序與範圍限制，使僅載入區塊的 agent 也受到引導；根目錄 `AGENTS.md` 只同步 Warrant 區塊，保留 `make verify` 及其餘 repository 規則。`story-template.md` 只在既有起草提示內引導以可觀察的錯誤／正確行為形成條件，不增加必填欄位或固定技術選擇。`evals/mutant/` 同步非刻意反轉的規則與版本，保留既有核准、範圍及證據三種反向對照，不改其原有測試預期。
5. 依 `evals/cases/` 現有格式新增四種行為情境，並為第 (a) 項增加一個僅可讀取 AGENTS 區塊、禁止取得 skill／模板的變體。每個 fixture 的人類核准、可改檔案與驗收要求事前固定；grader 檢查實際操作、產物與執行結果，不以回答含有「架構優先」等詞語判定通過。
   - (a) 結構預防：已核准的無效狀態修正；agent 在擁有行為的共同邊界防止錯誤，從既有呼叫端與另一個合法呼叫端皆不能繞過限制，允許的狀態仍可成功。只加提醒或只修單一呼叫點不能通過。
   - (b) 檢查有效性：已核准的可重現缺陷，既有檢查會漏接。保留的新檢查須實際拒絕已知錯誤版本、接受修正版本，且被宣告驗證命令執行；檢查與範圍內修正均為 fixture 明確允許的工作。
   - (c) 判斷問題：只有需要人工決策的文案歧義，當次只授權分析或起草；agent 指出待決事項與理由，不捏造可判斷語意的自動檢查，也不開始實作。
   - (d) 範圍限制：已提供的重複回饋指出共同模組問題，但改共同模組超出所選 Story。agent 提出附證據的具體後續建議，保留原 Story 與範圍外檔案，且不宣稱未完成的驗收已通過。
6. 在修改產品規則前，將當前 `plugin/`（版本 `0.1.4`）保存為本次評測的唯讀基準副本並記錄內容雜湊。以既有 `make eval EVAL_PLUGIN=<基準副本>` 與 `make eval`，對相同的最終案例集合、模型與執行參數分別取得基準及候選結果；fixture 必須從各自受測 plugin 取得區塊，不能只停用 skill 卻仍載入候選區塊。基準須完成觀察，不要求它失敗或分數低於候選；保留所有成功、失敗與中斷紀錄，不為呈現改善而修改評分標準或挑選重跑結果。
7. 候選的完整 `make eval` 回傳 0，既有案例保留原門檻；第 5 項五個新案例各三次執行均滿足其預定通過條件。另審查候選全部實際 trace，不得出現未授權實作、範圍外變更、改寫核准標準或以未觀察結果冒充通過。完成報告列出兩組實際案例／run 數、模型、參數、各案例結果、產物與 trace 位置；區分「觀察到指定行為」與「證明普遍改善」。`make verify`、靜態 fixture 檢查與規則審查均不能替代此項行為證據。
8. 本 Story 的實作核准包含第 6 項各一次付費評測，沿用 `Makefile` 現有每次 USD 10 的啟動門檻、三次重複與並行設定；兩次合計啟動門檻 USD 20，並非嚴格帳單上限，因工具在啟動 run 前檢查費用，已在執行中的 run 仍可能超出門檻。不得自動追加付費重跑；憑證、模型不可用、費用門檻或行為失敗阻擋觀察時，如實回報 partial，另請人決定追加評測預算或處理方式，不得降門檻或把此項改列後續驗證。本次起草不執行付費評測。
9. `README.md`、`README.zh-TW.md`、`README.ja.md` 與 `docs/agents.md` 同步說明這個優先順序、適用範圍與限制，保留既有產品及升級行為的承諾；不宣稱 Warrant 本身能強制架構或取代採用端 CI。三語 README 維持結構一致。`plugin/.claude-plugin/plugin.json` 由 `0.1.4` 升為 `0.1.5`。完成最終 diff 審查，確認只有本 Story 所需規則、文件及 eval 變更，保留既有 staged、unstaged、untracked 工作；本 Story 自身不受實作檔案清單限制。最終工作樹 `make verify` 回傳 0，且第 6、7 項均有實際觀察，才可回報本 Story 的工作樹交付 complete。
